# 中文玄幻网文写作

## 1. 最高原则

1. 当前用户明确指令 > 用户确认的正史 > 当前项目故事圣经 > 已确认章纲 > 通用写作建议。
2. 区分“正史、草稿事实、后续计划”。草稿中的新事实只有被用户接受后才进入正史。
3. 用户提供的书名、人物名、样稿、路径、文档和桥段默认只是理解规则的素材。除非用户明确要求建立项目专属配置，否则不得写入 Skill 描述、触发路由、门禁、模板、测试或通用参考。
4. 不承诺“爆款”。只说明完成了哪些结构、语义或机械检查；真实留存、付费和市场效果需要发布后的读者数据。
5. 公式是诊断与设计工具，不替代因果和人物选择。[references/core-contracts.md](references/core-contracts.md) 明确标为硬锁的数字配额、[references/prose-style.md](references/prose-style.md) 的正文风格默认目标和 [references/revision-continuity.md](references/revision-continuity.md) 的连续性默认参数生效；可覆盖项必须在任务卡显式记录新值，除此之外的数字只有用户明确启用后才生效。
6. 不因作者偏好擅自禁用用户允许的叙事材料。涉及牺牲、复仇、哭泣、敏感玩笑或回忆中新揭信息时，检查因果、人物尊严、语气、来源链与连续性，但不自动判禁写。
7. 读者正文与编辑控制层永久隔离：规则名、约束 ID、自检宏、PASS/FAIL、公式拆解和审计表只能存在于内部工作区或独立 QA 侧车，绝不能进入小说标题、正文段落或正文文件。
8. 未另行指定时，每章必须独立达到 2000–3200 个净正文有效字符；不得用标题、标点、Markdown、注释、代码块、审计文字或其他章节篇幅补足。
9. 正文默认执行去模板化审校，但不得把候选词命中当成 AI 作者身份判断。风格目标可由风格卡按具体语境覆盖；不得机械删词或同义替换。
10. 长篇状态库是已接受正文的派生索引，不是第二真源。正文与状态冲突时停止续写、从正文重建状态；不得修改正文迁就旧账，也不得让内部状态标签进入读者正文。

## 2. 最小任务卡

开始前记录：

- 任务：规划 / 正文 / 续写 / 重写 / 审校 / 设定 / 保存文件
- 范围：全书 / 卷 / 章 / 段落
- 类型、读者承诺与目标平台
- 爽点模式：订阅成长向 / 免费滑读向 / 超快脑洞向 / 情感关系向 / 通用平衡
- 斗智模式：主流玄幻 / 智斗权谋
- 叙事视角、时态、语气
- 连续性基线、状态文件与当前版本
- 本章时间锚、入口地点与场景 POV
- 去模板化强度与风格白名单
- 篇幅、逐章目标净字数、标题和文件要求
- 已确认正史、不可改项，以及用户显式启用或覆盖的公式、数值与特殊写法
- 未知项与可安全假设

资料足够时直接工作；只有缺失信息会实质改变结果时才提问。

## 3. 直接加载路由

所有参考都由本入口直接一级加载；不得依赖 Reference 再转跳到另一个 Reference。

- 生成、续写、重写或审校任何小说正文：必须完整读取并执行 [references/core-contracts.md](references/core-contracts.md)。
- 规划全书、世界、力量、金手指、地图、秘境、高潮、命名、平台爽点模式或打脸四拍：读取 [references/story-design.md](references/story-design.md)。
- 设计人物、关系、反派、配角、爱情、人物弧或情绪：读取 [references/character-emotion.md](references/character-emotion.md)。
- 从零连续生成多章、续写、重写、跨场景创作、时间跳跃、多视角、回忆揭密或连续性核对：完整读取并执行 [references/revision-continuity.md](references/revision-continuity.md)。
- 生成、续写、重写或审校任何小说正文：完整读取并执行 [references/prose-style.md](references/prose-style.md)。
- 从零创作、前三章、前十章、章节正文或前 30000 字规划：完整读取并执行 [references/opening-retention-six-locks.md](references/opening-retention-six-locks.md)；其中九项留存硬锁默认强制并累积。
- 生成、续写、重写或审校任意章节正文：完整读取并合取执行 [references/chapter-rhythm-twenty-locks.md](references/chapter-rhythm-twenty-locks.md)、[references/chapter-rhythm-rules-21-30.md](references/chapter-rhythm-rules-21-30.md) 与 [references/chapter-rhythm-rules-31-60.md](references/chapter-rhythm-rules-31-60.md)。
- 维护或新增规则时：读取 [references/rule-registry.json](references/rule-registry.json)，修改唯一的人类可读规则真源，并运行 [scripts/validate_rule_registry.py](scripts/validate_rule_registry.py)；注册表只登记身份、来源、路由和控制词，不复制规则正文。
- 需要章卡或故事圣经时，复制并填写 [assets/chapter-card-template.md](assets/chapter-card-template.md) 或 [assets/story-bible-template.md](assets/story-bible-template.md)。

不要为了“可能有用”加载不适用的参考；同一任务命中多条路由时，合取执行全部命中项。

### 3.1 常用加载集合

以下集合只帮助路由，不改变上方逐项触发条件：

| 任务 | 必须加载 |
|---|---|
| 设定与全书规划 | story-design；涉及人物时再加 character-emotion |
| 单章正文 | core-contracts + prose-style + 三个章节节奏 Reference |
| 开篇、前三章、前十章 | 单章正文集合 + opening-retention-six-locks |
| 连续多章或续写 | 单章正文集合 + revision-continuity；命中开篇范围时再加开篇留存 |
| 重写既有正文 | core-contracts + prose-style + 三个章节节奏 Reference + revision-continuity |
| 仅做连续性审校 | revision-continuity；涉及正文改写时升级为重写集合 |

“完整读取”指读到文件末尾后再行动；不得只看标题、摘要或局部命中段。若参考之间出现表面冲突，先按第 4 节仲裁，不得通过少加载一个文件规避合同。

## 4. 规则作用域与仲裁

1. 核心合同、开篇留存合同、六十项章节节奏锁、平台模式、风格合同和连续性合同并列累积；新规则只能收紧或补充，不得静默替换、删减或放宽旧规则。
2. 用户显式覆盖只对其明确指标和范围生效，并写入任务卡；未被覆盖的合同继续生效。
3. 正史使某项确实不适用时，在 QA 侧车写“未触发：具体原因”；未到期的跨章门槛写“尚未到期，已规划”，不得登记 PASS。
4. 两项规则冲突时，依次按正文纯净与安全、正史连续性、用户显式目标、核心因果、较严格可同时满足阈值仲裁；无法兼容时停止交付并说明冲突，不私自牺牲任一硬锁。
5. 机械审计只证明其可检测候选，不证明文学质量、人物动机、爽点语义、市场留存或作者身份。

## 5. 统一执行流程

### 5.1 规划与章前预检

1. 明确一句话承诺：谁在什么压迫下，靠什么独特行动获得何种持续满足。
2. 建立因果骨架：缺口 → 选择 → 代价 → 状态变化 → 新问题。
3. 建立最小系统：力量来源、成长接口、资源约束、能力边界和失败后果。
4. 建立人物驱动：主角欲望与底线、关系对象的独立目标、对手的行动逻辑。
5. 长篇任务载入状态 N，建立本章状态切片、时间与位置入口、场景 POV、允许出场人物、关键帧、一个主任务和最多一个副任务；连续多章时维护滚动三章状态表，每章只承担有限且符合已加载密度锁的新增信息。
6. 预检当前范围会触发的开篇、代价、智斗、事件、伏笔、滚动窗口与跨章门槛；只在内部建立检查账。

### 5.2 正文生成

1. 按“本章目标 → 阻力 → 行动 → 结果或代价 → 反转或钩子”推进，每章至少改变一个可追踪状态。
2. 默认单场景单 POV；角色只能按当时已知且有来源的信息行动。
3. 设置、风格、节奏、人物和连续性合同在生成过程中同步执行，不在正文打印控制标签。
4. 标题服务于本章独有动作、代价或反转，避免只换名词的万能标题。
5. 任一硬锁失败，只回滚其触发范围并真实重写；不得用修订建议、审计文字或未来伏笔冒充修正。

### 5.3 章后提交与复检

1. 提取人物、物品、地点、知情、时间、伤势、关系、承诺、债务、期限、移动、伏笔、新设定和剧情阶段增量；每项增量都绑定触发事件与正文来源。
2. 执行正向回放、逆向举证、逻辑反证、人物一致性、设定与普通读者五镜审校。
3. 修改旧章时，从最早受影响锚点失效并重放下游状态；回溯未完成或硬冲突未清零时不得宣称连续性通过。
4. 先移除控制层污染，再对最终版本逐章计算净正文有效字符。
5. 不足时扩写会改变选择、阻力、关系、信息或战后状态的完整因果单元；超限时删去重复解释和不改变状态的段落。
6. 去模板化改写后重新运行纯净门禁、逐章计数和相关状态验证；旧的 PASS 不得沿用。
7. 所有已触发、已到期规则通过后，才提交状态 N+1 和最终正文。

### 5.4 失败与回滚边界

- 路由缺失：停止生成，补齐适用 Reference 后从章前预检重新开始。
- 正史或状态冲突：停止续写，从已接受正文重建状态，不修改正文迁就旧账。
- 语义硬锁失败：定位最早失败证据，只重写受影响场景并重放其后的状态增量。
- 正文污染：先移出全部控制文字，再重新计数；不得只把污染隐藏为注释或代码块。
- 字数不足：补完整因果节拍；禁止堆景物、复述前情、复制句子或插入无效对白。
- 字数超限：压缩重复解释和不改变状态的段落；不得删除关键代价、选择或回报证据。
- 机械检查与人工判断冲突：保存机械结果并做语义复核；不得伪造 PASS，也不得让正则候选直接判定作者身份。
- 用户要求直接交付时，仍在内部完成回滚与复检；黑匣子模式不豁免合同。
- 硬性阻塞：直接说明阻塞项、已完成项和下一步，不用创作术语包装未完成状态。

## 6. 编辑黑匣子与套路管理

- 用户要求“直接生成”“不要解释过程”或“黑匣子模式”时，内部仍执行任务卡、因果骨架、状态事务和审计；最终只交付成品及必要验证摘要。
- 正文交付前不展示大纲、公式、章卡或套路分析，除非用户明确要求查看。
- 章前复述、状态卡、关键帧、状态机、规则拆解、平台公式、词频统计、改写理由和逐项自检只进入内部工件或 QA 侧车。
- 常见套路必须登记功能、前三章可见证据、限制与代价、主线交叉、删除条件和状态；删去套路后因果不变时应降级或移除。
- 固定数量、固定热词、题材组合或额外章位仅在用户显式启用时生效；核心合同已有硬阈值不受此句豁免。
- 不把结构齐备、机械通过或公式命中表述为“爆款”“必火”或市场验证。

## 7. 长篇、人物与改稿底线

- 用总纲、卷纲和滚动章纲分别约束终局、阶段与当前章节，不让计划倒灌成事实。
- 人物通过压力下的选择立住，不靠旁白宣布性格；配角有独立目标、拒绝权、生活与后果；反派的行动服从其信息、资源、期限和私人利益。反派动机可以理解，但理解不等于免责，其行为仍须承担后果。
- 情绪点必须改变关系、认知、目标或行动。悲伤不按性别限制停留时间；喜剧和敏感材料服从人设、因果、尊严及用户语气，不按作者偏好机械判禁，也不得抹掉弱势角色的主体性。
- 回忆中新揭信息必须有可核对的知情者、载体、时间线和前文兼容性；不得用无来源的新事实临时修补漏洞。
- 局部改稿优先最小改动，不顺手重写无关段落；续写新事实保持“草稿事实”，被用户接受后才进入正史。
- 大境界或大地图变化至少改变可解决问题、代价、社会权限、敌方行动或旧关系责任之一，不能只换数值。
- 审校分开报告连续性、因果与能动性、节奏与回报、语言候选、平台适配证据，以及无法由文本证明的读者或市场判断。

## 8. 正文、状态与 QA 隔离

1. 正文只含批次标题清单、章标题和小说正文；正文标题、段落或文件不得出现约束 ID、规则名、PASS/FAIL、自检宏、状态卡、JSON、公式拆解或审计表。
2. 状态使用独立的 .state.json；QA 使用独立的 .qa.json；两者的任何字符不得计入正文。
3. 旧合同中的“附上自检”永久解释为写入独立 QA 侧车或内部记录，绝不解释为拼接在小说末尾。
4. 未另行指定时，每章独立 2000–3200 个净正文有效字符；三章总和、平均值或其他长章不能补偿短章。
5. 净正文只统计小说叙事中的汉字、其他文字字母和数字；标题、标点、空白、Markdown、HTML 注释、代码块、链接地址、编辑说明和控制文字不计。
6. 起稿按每章约 2200–2800 个净正文有效字符留余量；人工估算不算验收，必须在最终保存版本逐章实测。
7. 聊天展示与保存文件必须来自同一份已通过版本；不得先展示短稿、再只在文件补字。
8. 只要正文泄漏一个控制标签，或任一章低于 2000 / 高于 3200，交付即无效；先修正并重跑审计。

## 9. 确定性审计

审计脚本只检查可机械识别的候选，不证明文学质量、人物弧或市场效果。

    python3 scripts/audit_chapter.py <正文文件> --json-out <正文同名.qa.json>

检查前三章结构、标题和默认字数窗口：

    python3 scripts/audit_chapter.py <正文文件> \
      --require-title \
      --require-opening-three \
      --min-effective 2000 \
      --max-effective 3200 \
      --opening-min-effective 2000 \
      --opening-max-effective 3200 \
      --json-out <正文同名.qa.json>

任务卡显式设置单章目标时，另加 --target-effective <正整数>；其正负 20% 窗口与绝对窗口取交集。

含已提交事件或关键帧的状态文件另运行：

    python3 scripts/validate_story_state.py <当前.state.json> \
      --prose <最终正文.md> \
      [--previous <上一.state.json>] \
      --json-out <当前.qa.json>

非初始状态必须提供 --previous。脚本实算最终正文原始字节哈希和来源段落哈希，并检查结构、引用、版本链、当前关键帧及部分显式状态约束；之后仍须人工核对连续性语义、正史、因果和人物选择。

## 10. 交付

- 先给成品，再给必要验证摘要。
- 用户要求保存时，聊天正文与文件内容来自同一最终版本。
- 正文成品只含小说内容；机械报告和逐项证据保存为独立 QA 侧车。默认摘要只报告逐章净字数和纯净门禁，不回显约束 ID。
- 需要长篇状态时，正文 .md、状态 .state.json、审计 .qa.json 三分离。
- 明确写出已完成、已验证、未验证和仍需用户决定。
- 未在最终保存版本运行审计时，不得报告字数或纯净门禁通过。
- 不把“通过门禁”写成“已是爆款”。
